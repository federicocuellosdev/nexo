# Nexo 3.0 — Maqueta clickeable (landing + portal) — Diseño

Fecha: 2026-09-07 · Estado: aprobado por Matias Yennerich (enfoque A) · Alcance: primera versión mostrable, recorrido completo.

Este documento es idéntico en `nexo-3.0-landing` y `nexo-3.0-portal`. Contexto de producto en `docs/CONTEXTO.md`.

## 1. Objetivo

Maqueta navegable, mobile-first, que recorre de punta a punta la experiencia de Nexo 3.0
"como si estuviera funcional", sin backend: home → catálogo → ficha → alta → magic link →
portal → pago → perfil → portal con las cinco secciones. Audiencia: Previnca (Federico
Cuellos, Javier Talarn). Federico conecta después backend, Magic Link, Supabase, MercadoPago
y Salesforce.

Fuera de alcance: portal de administración, auth real, pagos reales, SEO/SSG, i18n.

## 2. Decisiones

| Decisión | Elección | Motivo |
|---|---|---|
| Repos | Dos ramas huérfanas `nexo-3.0` (landing y portal), sin código de Nexo 2.0 | Decisión del usuario; aislamiento total de `main`/`staging` |
| Stack | Vite 7 · React 19 · TS strict · Tailwind v4 · React Router 7 · Radix (Dialog, Tabs) · lucide-react | Mismo stack que la landing 2.0 (Fede lo conoce); DX rápida; deploy estático |
| Animación | CSS transitions + `@starting-style`; sin Framer Motion | La 2.0 tiene rama `remove-framer`: ya pesó |
| Dispositivo | Mobile-first; desktop en segunda pasada dentro de cada tarea | El usuario real contrata desde el celular |
| Identidad | Evolución visual: paleta y tipografía heredadas, dirección "app/fintech" | Acordado con Fede reaprovechar look&feel; el portal es estilo MercadoPago |
| Compartir UI entre repos | Duplicación 1:1 de `styles/` y `ui/` | Dos repos huérfanos; un paquete compartido no se justifica para una maqueta |
| Handoff landing→portal | Parámetros de URL en `/auth/callback` | Orígenes distintos: `localStorage` no se comparte; imita un magic link real |
| Catálogo | Una página `/catalogo` con tabs Planes / Productos | Fede dejó abierto "uno o dos catálogos"; la tab resuelve sin cerrar la decisión |
| Datos pendientes | Chip visible "a confirmar" | No ocultar ni inventar datos que el cliente no confirmó |

## 3. Arquitectura (idéntica en ambos repos)

```
src/
  main.tsx            monta React Router
  router.tsx          definición de rutas (createBrowserRouter)
  styles/
    tokens.css        @theme de Tailwind v4: colores, radios, sombras, easings, fuentes
    fonts.css         @font-face DM Sans / DM Serif Display (public/fonts/*.woff2)
    global.css        reset mínimo, body, focus-visible, reduced-motion
  ui/                 primitivos SIN dominio (no conocen planes ni sesión)
    Button Card Badge Chip Field Input Select Sheet Dialog Tabs
    BottomNav Sidebar TopBar EmptyState Skeleton Money Icon
  features/           organismos CON dominio
    planes/           PlanCard PlanPrestaciones PlanComparador ProductoCard
    alta/             AltaDialog (popup usuario base) RevisaTuMail
    perfil/           PerfilWizard (4 pasos) + campos
    cobertura/        CoberturaCard CoberturaEstado
    movimientos/      MovimientoRow MovimientosList
    novedades/        NovedadesCarousel
  pages/              una por ruta; solo compone features y layout
  layouts/            PublicLayout (landing) · PortalLayout (portal)
  mock/               fixtures + session store
    planes.ts productos.ts novedades.ts usuarios.ts session.ts
  lib/                cn.ts formato.ts urls.ts
test/                 setup de Vitest; e2e/ con Playwright
public/fonts/         woff2 auto-hospedadas
```

Regla de dependencia: `pages → layouts/features → ui`. `mock/` y `lib/` son hojas.
Importar `mock/` desde `ui/` está prohibido.

Cada unidad responde: qué hace, cómo se usa, de qué depende. Un archivo grande es señal de
que hace demasiado.

## 4. Handoff entre aplicaciones

Landing y portal corren en orígenes distintos (dev: `:5173` y `:5174`; Vercel: dos dominios).

Landing → portal: al enviar el popup de alta, la landing navega a `/revisa-tu-mail`. El botón
"Abrir el mail (demo)" abre:

```
{PORTAL_URL}/auth/callback?token=demo&intent=alta&tipo=plan|producto&id=<slug>
  &nombre=&apellido=&email=&tel=
```

Login ("Ya tengo cuenta"): `{PORTAL_URL}/auth/callback?token=demo&intent=login&email=`.

El portal parsea (`lib/callback.ts`), siembra la sesión y redirige:
`intent=alta` → `/bienvenida`; `intent=login` → `/inicio`.

Portal → landing: "Ver catálogo" y "Cerrar sesión" (limpia la sesión) → `{LANDING_URL}`.

URLs por variables `VITE_PORTAL_URL` / `VITE_LANDING_URL`, con defaults de desarrollo.

## 5. Sesión mock (portal)

`mock/session.ts`: store con `useSyncExternalStore`, persistido en
`localStorage["nexo3.session"]`. API: `getSession() · setSession(patch) · resetSession() ·
seedDemo(perfil) · useSession()`.

```ts
type Session = {
  usuario?: { nombre: string; apellido: string; email: string; telefono: string };
  perfil?: PerfilPrevinca;                 // completo ⇒ cobertura activa
  intent?: { tipo: 'plan' | 'producto'; id: string };
  ordenes: Orden[];
};
type Orden = { id: string; fecha: string; tipo: 'plan' | 'producto'; itemId: string;
               concepto: string; monto: number; estado: 'pagada' | 'pendiente' };
type PerfilPrevinca = {
  tipoDocumento: 'DNI' | 'Pasaporte'; numeroDocumento: string;
  sexo: 'F' | 'M' | 'X'; fechaNacimiento: string;
  domicilio: { calle: string; numero: string; piso?: string; localidad: string; provincia: string; cp: string };
  tieneObraSocial: boolean; obraSocial?: string;         // en debate: se pide, no es obligatorio
  tipoContratacion: 'beneficiario' | 'tomador' | 'tomador-beneficiario';
};
```

Estados derivados (`lib/estado.ts`): `sinCuenta` · `conCuentaSinPago` · `pagadoSinPerfil`
(cobertura *pendiente de activación*, banner persistente "Completá tu perfil") · `activo`.

Guards de ruta: sin `usuario` → `/ingresar`. `/bienvenida` sin `intent` → `/inicio`.

`/demo`: botones "Reiniciar", "Usuario nuevo con intención Nexo II", "Usuario con Nexo II
activo" para saltar estados durante la presentación.

Landing: solo guarda `intent` en `sessionStorage` mientras el popup está abierto.

## 7. Dirección visual

Heredado de Nexo 2.0 (`docs/referencia/theme.nexo-2.0.css`): purple `#8660ef`, pink
`#ee5cd0`, peach `#e5ab9f`; DM Serif Display para display; DM Sans para todo lo demás;
radios 16 / 10 / pill; sombras suaves en cuatro niveles; easings out-expo / out-quart.

Nuevo en 3.0:
- Fondo de app `#f6f5fb`; superficies blancas; escala neutra `ink-950…ink-50`.
- Semánticos: `ok` (verde), `warn` (ámbar, para "a confirmar" y "pendiente"), `danger`.
- El degradado de marca queda reservado al CTA primario y a acentos (avatar, icono de
  cobertura). No fondos completos degradados.
- Densidad de aplicación: listas con icono en círculo, chips de estado, cards con título +
  dato grande + acción secundaria (patrón MercadoPago).
- Tipografía: escala 12 / 14 / 16 / 20 / 24 / 32 / 40; `Money` con decimales en superíndice.
- Motion: entradas de sheets/dialogs con `@starting-style`; transiciones 200–300 ms;
  `prefers-reduced-motion` desactiva desplazamientos y deja solo opacidad.
- Accesibilidad: foco visible, contraste AA, labels reales, `aria-current` en navegación.

## 8. Datos mock

- `mock/planes.ts`: porta SOLO los bloques `PLANES` y `ON_DEMAND` de
  `docs/referencia/planes.nexo-2.0.ts` con tipos redefinidos aquí. No se portan `formatearMiles`,
  `LS_PLAN_KEY` ni `PRECIO_DESDE` (mecánica del 2.0). `PRECIO_DESDE` se recalcula en `lib/`.
- Flags `pendiente: true` → chip "a confirmar". Datos afectados hoy: Óptica en Nexo I, Médico a
  domicilio en Nexo II, precio de Árbol de Vida, precio de Seguro de Vida.
- `mock/novedades.ts`: 3 novedades ficticias. `mock/usuarios.ts`: perfil demo "Camila Pérez".
- Todo texto de fixture es claramente demo; nada se presenta como dato real del cliente.

## 9. Testing

- Vitest + Testing Library (jsdom). TDD por tarea.
  - `mock/session`: seed, patch, reset, persistencia, derivación de estado.
  - `lib/callback`: parseo de query válida/incompleta.
  - Guards: redirección sin sesión.
  - `AltaDialog`: validación de campos, toggle "Ya tengo cuenta", submit navega.
  - `PerfilWizard`: avance/retroceso, validación por paso, guardado final.
  - `formato`: precios con separador de miles determinista (sin `toLocaleString`).
- Playwright (`npm run e2e` en el repo landing): un test que levanta ambos dev servers y
  recorre `/` → ficha → alta → mail → callback → bienvenida → pago → éxito → perfil → inicio.
- `npm run build` sin warnings de tipo; `tsc --noEmit` en CI local.

## 10. Deploy (documentado; se ejecuta al autorizar el push)

Dos proyectos Vercel nuevos apuntando a los mismos repos GitHub, *Production Branch*
`nexo-3.0`, framework Vite, `vercel.json` con rewrite SPA (`/(.*)` → `/index.html`).
Env: landing `VITE_PORTAL_URL`; portal `VITE_LANDING_URL`. Los proyectos `*-staging`
existentes no se tocan; opcionalmente se agrega un *Ignored Build Step* para `nexo-3.0`.

## 11. Orden de construcción

1. Base común (ambos repos): scaffold Vite, tokens, fuentes, `ui/` primitivos, layouts, tests base.
2. Landing: mock de planes, Home, Catálogo, Fichas, AltaDialog, RevisaTuMail, handoff.
3. Portal: session store, callback, Ingresar, Bienvenida, Pago, Éxito, PerfilWizard.
4. Portal: Inicio, Planes, Coberturas, Movimientos, Cuenta, Demo.
5. E2E de punta a punta, pasada desktop, revisión visual, README de cada repo.
